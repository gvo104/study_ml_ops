# План v1 по мониторингу дрифта для текущей модели

## Кратко

Сделать отдельный контур мониторинга, который будет проверять, не "уплыли" ли новые обращения относительно данных, на которых обучалась текущая production-модель.

Для локального demo контур разделяется на три процесса:

- `predict-api` — существующее основное FastAPI-приложение с `/predict`
- `synthetic-api` — отдельное FastAPI-приложение с локальной LLM для ролей `generator` и `expert`
- `drift-runner` — внешняя оффлайн-задача, которая вызывает оба API, собирает synthetic stream и считает drift-метрики

Для демонстрации использовать синтетический поток из последних `100` обращений.

Важно: внутри `synthetic-api` используется **одна и та же локально загруженная модель `Qwen2.5-3B-Instruct GGUF`**, но в двух независимых ролях:

- `generator` — генерирует обращения "как пациенты"
- `expert` — независимо размечает эти обращения "как эксперт"

То есть архитектурно это не две разные модели, а **одна модель с двумя системными промптами и двумя режимами работы**. Основной `predict-api` эту LLM не загружает.

Сравнение делать не с произвольными эвристиками, а с `reference`-состоянием, собранным из последней обучающей выборки **до oversampling**.

Основных метрик будет ровно 3:

1. `Token Distribution Drift`
2. `Model-Expert Disagreement`
3. `Token-Label Association Drift`

## Смысл подхода

- `Reference baseline`
  Это эталонное состояние данных, на которых модель считалась нормальной.
  Смысл: сначала зафиксировать "как выглядел мир в момент нормального обучения", а потом сравнивать с ним новые окна данных.
  В этом проекте `reference baseline` надо понимать однозначно:
  это **train split последнего production-обучения до oversampling**, сохраненный как отдельный неизменяемый snapshot вместе с метаданными разбиения.

- `Sliding window`
  Это скользящее окно последних `100` обращений.
  Смысл: drift считается не по всей истории сразу, а по самым свежим данным, чтобы видеть текущее состояние модели.

- `Synthetic stream`
  Это искусственно сгенерированный поток обращений.
  Смысл: пока нет полноценного production-потока и ручной разметки, можно эмулировать рабочую систему через отдельный `synthetic-api` и показать, как мониторинг будет срабатывать.

- `Phased drift scenario`
  Это сценарий, где данные меняются по фазам, а не хаотично.
  Смысл: сначала показать нормальный поток, потом постепенно ввести разные типы сдвига и проверить, что мониторинг реагирует именно тогда, когда должен.

- `Alert thresholds`
  Это пороги, после которых система считает, что drift уже значимый.
  Смысл: не объявлять drift "на глаз", а заранее определить, какой уровень отклонения еще нормален, а какой уже нет.

## Что именно реализовать

- Взять последнюю production training set как `reference`.
  Использовать реальные колонки проекта:
  - `statement`
  - `tokens_stemmed`
  - `status`
  - `num_of_characters`
  - `num_of_sentences`

- Зафиксировать, что `reference` — это не весь CSV целиком и не oversampled train.
  Это должен быть отдельный snapshot:
  - train split после `train_test_split`
  - до `RandomOverSampler`
  - с тем же `random_state`, что использовался в production-обучении
  - с сохраненными метаданными: дата, конфиг, hash датасета, random seed

- Построить из reference базовые статистики:
  - частоты токенов
  - распределение классов
  - характерные токены для каждого класса
  - baseline-значения трех drift-метрик

- Организовать текущий поток как окно последних `100` обращений.
  Пересчитывать drift, например, каждые `10` новых обращений.

- Запустить синтетический поток по фазам:
  - Фаза A: обращения близки к обучающим данным
  - Фаза B: меняется лексика, стиль, словарь
  - Фаза C: меняется доля классов
  - Фаза D: слова начинают ассоциироваться с классами иначе, чем в обучении

- Использовать две независимые роли одной и той же модели:
  - `Generator`
    Генерирует текст обращения как пользователь
  - `Expert`
    Видит только текст и ставит label как эксперт-проверяющий

- Разнести ответственность между сервисами:
  - `predict-api` только обслуживает текущую production-модель классификации
  - `synthetic-api` только выполняет LLM-инференс для `generator` и `expert`
  - `drift-runner` вызывает `synthetic-api` для генерации/разметки, вызывает `predict-api` для предсказаний модели и считает drift вне API-сервисов

- После генерации synthetic текста обязательно прогонять его через **тот же preprocessing pipeline**, что используется в проекте:
  - очистка текста
  - токенизация
  - stemming
  - формирование `tokens_stemmed`
  - вычисление `num_of_characters`
  - вычисление `num_of_sentences`

  Это нужно, чтобы drift считался в том же представлении данных, в котором обучалась модель.

- Если label эксперта не совпал с целевым сценарием генерации, обращение отбрасывать или перегенерировать.
  Смысл: поток должен оставаться управляемым и внутренне согласованным.

## Три главные метрики и что они значат

- `Token Distribution Drift`
  Это дрифт распределения токенов.
  Смысл: проверить, не начали ли пользователи писать другим языком, другими словами, другими формулировками.

  Как считать:
  - взять top `K=500` токенов из `tokens_stemmed` на reference
  - synthetic текст в текущем окне сначала прогнать через production preprocessing
  - посчитать частоты токенов в текущем окне
  - сравнить распределения через `Jensen-Shannon divergence`

  Что скрывается за названием:
  - `distribution` = как часто встречаются слова
  - `drift` = насколько это распределение изменилось
  - `Jensen-Shannon divergence` = мера различия двух распределений; чем выше значение, тем сильнее изменился словарь входящих обращений

- `Model-Expert Disagreement`
  Это расхождение между текущей моделью и экспертом.
  Смысл: даже если текст стал другим, главный практический вопрос — стала ли модель чаще ошибаться на текущем потоке.

  Как считать:
  - модель предсказывает класс
  - экспертная LLM ставит свой класс
  - считаются:
    - `disagreement_rate` — доля несовпадений
    - `macro-F1` — среднее качество по всем классам без перекоса в пользу частых классов

  Что скрывается за названием:
  - `disagreement` = насколько часто модель и эксперт не согласны
  - `macro-F1` = качество, где каждый класс важен одинаково; это важно, потому что классы у вас несбалансированы

- `Token-Label Association Drift`
  Это дрифт связи между словами и метками.
  Смысл: не просто слова стали другими, а изменилась сама семантическая связь "какие слова характерны для какого класса".

  Как считать:
  - для каждого класса на reference посчитать, какие токены наиболее характерны
  - использовать `log-odds` для оценки силы связи токена с конкретным классом
  - взять top `50` характерных токенов на класс
  - в текущем окне пересчитать эти же связи
  - измерить среднее абсолютное изменение

  Правило устойчивости для редких классов:
  - если в текущем окне для класса меньше `5` примеров, метрика для этого класса не считается
  - класс получает вес `0` в агрегированном score
  - итоговый `Token-Label Association Drift` считается по оставшимся классам
  - если после фильтрации осталось меньше `3` классов, статус этой метрики помечается как `insufficient_data`

  Что скрывается за названием:
  - `association` = связь между словом и классом
  - `log-odds` = статистическая мера, показывающая, насколько токен характерен для конкретного label по сравнению с остальными
  - если раньше слово было сильным сигналом `Anxiety`, а теперь чаще встречается в `Stress`, эта метрика должна это поймать

## Логика порогов и алертов

- Сначала прогнать `20-30` окон без внедренного drift, только на фазе A.
- По ним оценить нормальный разброс значений для каждой из 3 метрик.
- Выставить пороги:
  - `warning` — примерно на уровне `95-го перцентиля`
  - `critical` — примерно на уровне `99-го перцентиля`

Смысл:

- `percentile` показывает, какие значения бывают "обычно"
- если новое значение выше почти всех нормальных окон, это уже сигнал drift

Итоговый статус:

- `ok` — все 3 метрики в норме
- `warning` — хотя бы 1 метрика вышла за warning
- `critical` — 2 и более метрики вышли за warning, либо 1 ушла за critical
- если `Token-Label Association Drift` имеет статус `insufficient_data`, итоговый статус считается по двум остальным метрикам, а в summary явно записывается причина

## Что должно получаться на выходе

- JSON summary для машины:
  - размер окна
  - фаза сценария
  - 3 значения drift-метрик
  - статус каждой метрики
  - общий статус `ok/warning/critical`
  - признак `insufficient_data`, если какая-либо метрика не смогла быть устойчиво оценена

- Человекочитаемый отчет:
  - какие токены сильнее всего изменились
  - где модель чаще расходится с экспертом
  - для каких классов изменилась связь слов с labels

## Проверки

- На фазе A система должна в основном показывать `ok`.
- На фазе B первой должна расти метрика `Token Distribution Drift`.
- На фазе C должна сильнее расти метрика `Model-Expert Disagreement`.
- На фазе D должна особенно заметно расти `Token-Label Association Drift`.
- После возврата к нормальному потоку статусы должны постепенно возвращаться к `ok`.

## Допущения

- Это демонстрационный контур, а не финальная production-оценка.
- LLM-эксперт считается прокси-разметкой, а не заменой реального врача.
- Для v1 окно фиксировано: `100` обращений.
- Drift считается оффлайн отдельной задачей, не внутри `/predict` и не внутри `synthetic-api`.
- LLM-runtime живет внутри отдельного `synthetic-api`, а не внутри основного `predict-api`.
- `drift-runner` является **отдельной внешней задачей**, которая вызывает `synthetic-api` для генерации/экспертной разметки, вызывает `predict-api` для предсказаний и считает метрики вне основного inference-пути.
